🖥️ CarDex In-Game Computer Investigation

Goal: Determine whether a CarDex app can run natively inside the in-game office computer without rewriting the game's existing functionality — and if not, confirm the fallback (a standalone CarDex overlay widget).

Runs on: the machine with Car Dealer Simulator installed (not this workstation).

0. What We Are Deciding

The office computer is a world-space UMG widget. Everything hinges on one question:

Is the computer a navigable "app launcher / OS screen" (a list of app buttons that open apps), or a fixed set of screens hard-wired into the widget graph?

That answer selects the path:

Path What it means Rewrite needed?
A — Standalone overlay widget A UMG CarDex widget we spawn on top (via hotkey or on computer interact). Touches nothing the game already does. No
B1 — Extend a real launcher If the computer is a data-driven app launcher, add a CarDex entry + button alongside the existing apps. No
B2 — Replace/hook a fixed screen Swap hard-wired screens. Would mean recreating existing computer functionality. Yes (down-prioritized)

Decision rule: pursue B2 only if the computer is confirmed to be a navigable launcher and B1 applies. If it is a fixed screen, stop at Path A. B2 is out of scope by default because it requires rewriting existing functionality.

1. Prerequisites

  • FModel (latest) — fmodel.app
  • ZenTools (by Archengius) — needed if FModel cannot directly export cooked Zen/IOStore assets.
  • UE4SS zDEV build — required for the runtime dumper and the Lua probe. You already use UE4SS for SaveSync. The dev build is what enables the UHT/C++ header dumper.
  • The game at CarDealerSimulator/Binaries/Win64/.

2. File Inspection with FModel

  1. Launch FModel and open the CDS installation, pointing it at the game's Content/Paks/ folder.
  2. If property names are unversioned, load the *.usmap mapping generated by the UE4SS dumper (Settings → Mappings → custom).
  3. Use the folder tree (or search) to look for the computer/UI assets under the Content/UI, Content/Widgets, or Content/Blueprint trees.

Search keywords

Computer  PC  Screen  Desktop  OS  Launcher  App  Ui  UI  Widget  HUD  Office

What to collect

  • The Widget Blueprint class for the computer's main screen.
  • The owning actor/BluePrint (the physical computer actor) and its interaction component.
  • Any child widget classes that look like individual "apps" (finance, paint, phone, etc.).

Export the relevant .uasset files and open them in ZenTools/UAssetGUI to introspect the widget graph and the owning actor.

3. Runtime Probe with UE4SS

File inspection shows what exists; the runtime probe shows what is actually instantiated when you interact with the computer. This is the most definitive evidence for the launcher-vs-fixed-screen question.

Probe plan (single comprehensive script):

  1. When you interact with / look at the computer, find the computer's widget instance in memory.
  2. Print its class name and its child widget tree (reflection).
  3. List all loaded UUserWidget classes whose names contain computer/app/screen/OS keywords.
  4. Look for any representation of an "app list / launcher" (a grid/tile of buttons that open other widgets via Create Widget(class)).

The Lua probe script

Save the following as ComputerProbe/main.lua inside your UE4SS Mods/ folder, and enable it in mods.txt by adding ComputerProbe: 1. Trigger it with the default key (F10, overridable in RegisterKeyBind).

This script is a starting point. Class names and reflection APIs vary between UE4SS versions and game builds — adjust accordingly.

local UEHelpers = require("UEHelpers")

-- Target keywords that identify the computer / app / screen widgets.
local KEYWORDS = { "Computer", "PC", "Screen", "Desktop", "OS", "Launcher", "App", "Widget", "Office" }

print("[ComputerProbe] Loaded. Press F10 while facing the office computer.")

local function matchesKeywords(name)
    if not name then return false end
    for _, kw in ipairs(KEYWORDS) do
        if name:lower():find(kw:lower(), 1, true) then
            return true
        end
    end
    return false
end

-- Recursively print a widget's class + children up to a depth limit.
local function dumpWidgetTree(widget, depth, maxDepth)
    if not widget or depth > maxDepth then return end
    local class = widget:GetClass()
    local name = widget:GetName()
    local pad = string.rep("  ", depth)
    print(pad .. class:GetName() .. " :: " .. name)
    -- UWidget has a 'Slate' slot hierarchy; iterate child widgets if present.
    local prop = widget:FindProperty("WidgetTree")
    if prop then
        local tree = widget:GetPropertyValue("WidgetTree")
        -- Recursively walk known container widgets.
        local children = widget:GetAllChildren()
        if children then
            for _, child in ipairs(children) do
                dumpWidgetTree(child:GetOuter() or child, depth + 1, maxDepth)
            end
        end
    end
end

local function onComputerActivated()
    -- Find the player controller and all user widgets to identify the computer.
    local pc = UEHelpers.GetPlayerController()
    if not pc then print("[ComputerProbe] No player controller."); return end

    print("=== [ComputerProbe] Loaded user widget classes ===")
    -- Collect loaded widget classes by scanning the object tree.
    local all = StaticFindObject("UserWidget")
    -- In practice, iterate via the object database / registry in later UE4SS:
    -- see FindAllObjects / ObjectDumper docs for your UE4SS version.
    if all then dumpWidgetTree(all, 0, 6) end

    print("=== [ComputerProbe] Filtered by keywords ===")
    -- Deep search of the whole object tree for matching classes is available
    -- via FindAllObjects() in newer UE4SS; print those matching KEYWORDS here.
end

RegisterKeyBind(RegisterKey("F10"), function()
    onComputerActivated()
end)

Key bind note: the exact key name and the object-listing API differ across UE4SS releases. In newer UE4SS, replace the placeholder object listing with the object-database iterator (e.g. FindAllObjects / the object dumper) to enumerate every loaded UUserWidget and filter by KEYWORDS.

Because RE must run on the machine that has the game, iterate here: run the probe, paste the printed class names/widget tree back here, and we refine the script to target what you actually see.

FindingOutcome
Computer is a data-driven launcher we can add entries to GO B1 — build a native CarDex "app" added to the launcher. No rewrite.
